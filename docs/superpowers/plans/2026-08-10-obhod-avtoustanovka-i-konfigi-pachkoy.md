# План: автоустановка обхода БС + выдача конфигов пачкой

Дата: 10.08.2026
Основание: решения Влада 10.08 — «БС надо делать, и автоматически должно
ставиться, работает или нет как раз может решать тумблер», «конфиги объедини
в одно сообщение».

## Что уже проверено руками (это спецификация, а не догадки)

Обход поставлен на германскую ноду 10.08 вручную; последовательность шагов
ниже повторяет то, что реально сработало:

1. бинарь `/usr/local/bin/wdtt-server` (8.2 МБ) залит по SFTP с ноды бота,
   `chmod 755`;
2. юнит `/etc/systemd/system/wdtt.service` с
   `-listen 0.0.0.0:56000 -wg-port 56001 -config-dir /etc/wdtt -password <свой> -dns <dns>`;
3. `daemon-reload` + `enable --now`;
4. порты 56000/56001 udp в ufw;
5. проверка: `systemctl is-active wdtt` = active И `wdtt-server ctl -op list`
   отвечает `{"ok":true}`; после этого бот успешно создал и снял доступ.

Ключевой факт из исходника (`/root/wdtt-server-src/main.go`): при пустом списке
активных паролей демон падает с `[WRAP] нет активных паролей для WRAP`.
Значит `-password` обязателен при первом запуске — пароль владельца
генерируем случайным.

Второй факт: `harden.sh apply-firewall` строит правила от `listening_ports`,
поэтому обход надо поднимать ДО приведения к эталону — тогда его порты
попадут в фаервол сами. Обязательными аргументами их передаём только когда
демон реально поднялся: `apply-firewall` отказывается включать фаервол,
если обязательный порт не слушает.

## Задача 1. `SSHClient.put_file` — заливка двоичного файла

`write_file` умеет только текст, а бинарь 8 МБ. Добавить рядом `put_file`
(локальный путь → удалённый, права задаются при создании, как в `write_file`).

Тесты (`tests/test_ssh_put_file.py`): права выставляются при создании, а не
после; содержимое совпадает байт в байт; ошибка SFTP превращается в `SSHError`.

## Задача 2. `bot/services/wdtt_install.py`

`async def install(ssh, *, ports, dns, progress) -> bool`:

- если служба уже активна и `ctl -op list` отвечает — вернуть True, ничего не
  трогая (идемпотентность, как у эталона);
- иначе: залить бинарь → написать юнит с новым паролем владельца
  (`secrets.token_urlsafe(15)`) → `daemon-reload` → `enable --now` → подождать
  и проверить `is-active` + `ctl -op list`;
- пароль владельца НЕ логировать и не показывать в сообщениях бота.

Тесты (`tests/test_wdtt_install.py`, поведенческие на фейковом SSH):
идемпотентность; порядок шагов; False при неподнявшейся службе; False при
молчащем управляющем сокете даже у активной службы; пароль не попадает в лог.

## Задача 3. Мастер установки зовёт обход

В `bot/handlers/install.py` между READY и приведением к эталону:

- `wdtt_install.install(...)`;
- успех → `server.wdtt_enabled = True`, порты обхода уходят в `harden`
  как обязательные;
- неудача → тумблер остаётся выключенным, в итоговом сообщении отдельная
  строка «обход БС не встал».

Для этого `hardening.harden` получает необязательный `extra_ports`.

Тесты (`tests/test_install_wdtt.py`): при успехе тумблер включён и порты
переданы в эталон; при неудаче сервер всё равно READY, тумблер выключен,
порты обхода в эталон НЕ переданы (иначе фаервол не включится вовсе).

## Задача 4. Выдача конфигов пачкой

`bot/handlers/config_delivery.py`:

- `ask_config_format_for_device(chat_id, session, device)` — один вопрос
  на устройство, callback `CB_CFG:<kind>:dev:<device_id>`;
- обработчик пачки: права по устройству, видимые активные пиры
  (`relocate.visible_peers`), файлы и QR — `send_media_group` группами по 10,
  ссылки — одно сообщение списком «локация — ссылка»;
- `cb_dev_send` перестаёт слать вопрос на каждую локацию.

Одиночный путь (`ask_config_format` по пиру) остаётся: им пользуются семь
других мест.

Тесты (`tests/test_config_delivery_batch.py`): один вопрос вместо N; файлы
уходят одной группой; больше 10 локаций — группами по 10; чужое устройство
не отдаётся; отозванные и доживающие после переезда конфиги не попадают
в пачку.

## Порядок

1 → 2 → 3 (обход), затем 4 (конфиги). После каждой задачи — полный прогон
тестов; QR-тесты в Termux падают без PIL, это фон.
