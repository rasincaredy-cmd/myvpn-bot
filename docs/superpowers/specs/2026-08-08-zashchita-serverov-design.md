# Защита и мониторинг серверов проекта

Дата: 08.08.2026
Статус: согласован, план не написан

## Зачем

При разборе жалобы на лаги VPN 01.08.2026 выяснилось, что сервер
`31.77.157.162` (единственный боевой, он же хост бота) стоит с настежь
открытой дверью. Замеры 01.08.2026:

- фаервол выключен (`ufw status` → `inactive`);
- защиты от перебора нет, fail2ban не установлен;
- вход под `root` **по паролю разрешён** (`permitrootlogin yes`,
  `passwordauthentication yes`);
- за сутки **17 152 неудачные попытки входа с 247 разных адресов**;
- истории нагрузки не было вообще, поэтому причину лагов установить
  не удалось — данные о прошлом отсутствовали.

Замеры 08.08.2026 при проектировании защиты:

- веб-панель x-ui (порт 6769) открыта всему интернету;
- журнал разросся до 3,9 ГБ.

На этом же сервере лежат бот, база с ключами клиентов и идёт согласование
платёжного провайдера. Компрометация означает потерю и клиентов, и согласования.

Задача — не разовая заплатка, а базовая настройка, одинаковая для всех
серверов проекта: и для работающих, и для тех, что появятся при росте.

## Решения

Приняты в обсуждении 08.08.2026:

| Вопрос | Решение |
| --- | --- |
| Вход под root по паролю | Бот заводит себе ключ, пароль выключается после проверки |
| Аналитика | Сбор истории + тревоги в телеграм |
| Выкат на боевой сервер | Через автооткат по таймеру |
| Способ доставки на серверы | Отдельный сценарий-эталон, вызывается из двух мест |
| «Сервер умер целиком» | Пока не закрываем, закроется появлением второго сервера |
| Панель x-ui | Доступна только через VPN |

## Архитектура

Один сценарий-эталон описывает, каким должен быть **любой** сервер проекта.
Он идемпотентен: повторный запуск приводит сервер к нужному состоянию
и ничего не ломает, если всё уже стоит.

Точек вызова две:

1. **Новый сервер** — автоматически, в мастере установки, сразу после
   AmneziaWG. Админ ничего не нажимает.
2. **Работающий сервер** — кнопкой в админке. Нужно для `31.77.157.162`
   и всех, кто уже в строю.

Правила безопасности живут в одном файле, а не размазаны по логике VPN:
их можно прочитать целиком и понять, что делается с сервером. Новое правило,
добавленное в эталон, автоматически действует и на новые серверы, и на старые
после прогона.

Ansible сознательно отвергнут: тащит инструмент с зависимостями на телефон
и сервер ради одного-двух серверов.

## Состав эталона

### 1. Замена пароля на ключ

Порядок критичен — пароль выключается **только после доказательства**,
что ключ работает:

1. сгенерировать отдельный ключ для этого сервера;
2. положить публичную часть на сервер;
3. **отдельным новым подключением проверить**, что вход по ключу работает;
4. только теперь выключить вход по паролю;
5. сохранить ключ в базу (Fernet, как остальные креды) и стереть пароль.

Если шаг 3 не прошёл — не менять ничего и сообщить админу, что сервер
добавлен, но не закрыт.

### 2. Банилка перебора

Белый список — кого не банить никогда:

- собственный внешний адрес сервера (бот ходит по SSH сам на себя, без этого
  он забанит себя первым же сбоем аутентификации);
- подсеть VPN `10.8.0.0/24`;
- подсеть обхода `10.66.66.0/24`.

Последние две — путь администратора внутрь, который останется живым, даже если
мобильный адрес сменится или банилка ошибётся.

### 3. Фаервол

Строится **от того, что реально слушает наружу**, а не по списку из головы —
это защищает от аварии «забыл разрешить нужный порт».

На `31.77.157.162` наружу смотрят (замер 08.08.2026):

| Порт | Служба |
| --- | --- |
| tcp/22 | SSH |
| udp/585 | AmneziaWG |
| udp/56000, 56001 | обход БС (wdtt) |
| tcp/8443 | MTProto |
| tcp/2096 | подписки x-ui |
| tcp/16044, 20476 | xray (клиентские подключения) |
| tcp/6769 | панель x-ui — **закрыть от интернета, оставить только из VPN** |

Фаервол включается последним действием и только после того, как нужные порты
уже разрешены.

### 4. Потолок журнала

Журнал разросся до **3,9 ГБ** — почти половина занятого места на диске
(`/var/log` — 4,3 ГБ из 9,2 ГБ). Главные писатели за сутки: x-ui — 86 412 строк,
sshd — 50 703 строки (стук переборщиков). Вторая половина исчезнет сама после
установки банилки, журналу нужен потолок.

Потолок: **500 МБ** на весь системный журнал. Этого хватает на историю
за несколько недель при текущем темпе записи; старые записи вытесняются
автоматически.

Места сейчас хватает (свободно 29 ГБ из 40 ГБ), но растёт он без ограничения,
а кончившийся диск кладёт сервер целиком.

### 5. Сбор статистики

Установлен 01.08.2026, уже работает: шаг 2 минуты, хранение 30 дней,
нагрузка процессора с долей соседа, память, диск, сеть.

Сверху добавить то, чего стандартный сбор не знает:

- потери на буферах приёма по каждому сервису;
- давность рукопожатий с клиентами;
- число забаненных адресов.

### 6. Тревоги в телеграм

Порог такой, чтобы сообщение означало «иди чини», а не «прими к сведению»:

- упал любой из сервисов: бот, VPN, обход БС, x-ui;
- свободного места на диске меньше 15%;
- доля процессора, отъедаемая соседом, выше 20% дольше 10 минут
  (обычный фон — 1,5–2%);
- память на исходе или система начала убивать процессы;
- резкий рост потерь пакетов;
- **бот или администратор попали в бан** — самая важная тревога.

Против спама: одна проблема — одно сообщение, повтор не чаще раза в час,
обязательное сообщение «отпустило». Иначе тревоги перестанут читать,
и это хуже, чем не иметь их вовсе.

## Безопасность выката

**Сухой прогон.** Сценарий умеет показать, что он сделает, ничего не меняя:
какие порты оставит, какие закроет, кого внесёт в белый список.
Для `31.77.157.162` это обязательный первый шаг.

**Автооткат.** Опасные шаги — выключение пароля и включение фаервола — идут
под таймером: сервер получает отложенную команду «верни как было через
10 минут». Проверка связи прошла — команда отменяется. Доступ потерян —
сервер откатывается сам, клиенты не замечают.

## Проверка

Сценарий не рапортует «готово» просто так. После прогона проверяется:

- вход по ключу работает;
- вход по паролю больше **не** работает;
- все нужные порты снаружи отвечают;
- бот успешно достучался до сервера;
- сбор статистики пишет файлы;
- банилка запущена, белый список в ней виден;
- панель x-ui снаружи недоступна, изнутри VPN — доступна.

## Известное ограничение

Бот живёт на том же сервере, за которым следит. Если сервер умрёт целиком
или потеряет сеть — тревогу отправлять будет некому, о простое станет известно
от клиентов. Самопроверка ловит всё, кроме собственной смерти.

Решено не закрывать это сейчас: дыра исчезнет сама, когда появится второй
сервер и они начнут проверять друг друга. Тащить сторонний сервис
или зависеть от включённого телефона ради временной ситуации не стоит.

## Что не входит

- Смена порта SSH — не даёт защиты, усложняет мастер установки.
- Двухфакторный вход — при выключенном пароле избыточен.
- Панель с графиками (Grafana и подобное) — съест заметную часть памяти
  и единственного ядра, через которое идёт весь VPN-трафик.

## Статус

Этап 1 (сценарий-эталон + закрытие боевого сервера) выполнен 08–09.08.2026.
`harden.sh check` на `31.77.157.162` даёт «сервер соответствует эталону»,
код возврата 0.

Что изменилось на боевом сервере:

- вход по паролю выключен, у бота отдельный ключ, пароль стёрт из базы;
- банилка перебора работает, в белом списке свой адрес и подсети VPN/обхода;
- фаервол включён, наружу открыты только рабочие порты, панель x-ui — из VPN;
- журнал ограничен 500 МБ (было 3,9 ГБ).

Урок, который стоил дороже всего: под `set -o pipefail` конструкция
`команда | grep -q ...` врёт НАОБОРОТ — `grep -q` закрывает трубу на первом
совпадении, источник получает SIGPIPE, и найденная строка читается как
ненайденная. Проверка рапортовала «вход по паролю РАЗРЕШЁН» на сервере, где
пароль уже был выключен. Закрыто страж-тестом `test_no_pipe_into_grep_q`.

Этап 2 (вызов из бота для новых серверов, кнопка в админке, тревоги
в телеграм) — отдельный план.
